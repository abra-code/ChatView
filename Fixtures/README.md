# ChatView cross-platform fixtures

These fixtures are the byte-level interop contract between the Swift ChatView (this repo,
normative) and the Kotlin/Compose port (`android/chatview`). They are generated by the Swift
emitter and asserted, unchanged, by both the Swift replay test and the Kotlin ports.

- Producer: `Tests/ChatViewTests/FixtureEmitterTests.swift`, `testEmitFixtures`, gated on the
  environment variable `CHAT_EMIT_FIXTURES=1`. Regenerate with:
  `CHAT_EMIT_FIXTURES=1 swift test --filter FixtureEmitterTests/testEmitFixtures`
- Swift guardrail: `FixtureReplayTests` (always runs) decodes every scenario stream with the
  test-only event codec, routes it through a live `ChatStore`, and asserts the result equals the
  committed `*.expected.json`; it also round-trips every transcript golden.
- Kotlin guardrail: the A3/A5 ports decode these same files. The Kotlin event decoder is written
  against THIS README, not against the Swift emitter's source.

All JSON is UTF-8, compact, with SORTED KEYS. Slashes are not escaped; non-ASCII (emoji) is
emitted as raw UTF-8 (not `\u` sequences), matching kotlinx.serialization's default. Every file
ends with a single trailing newline.

## Encoding conventions (the model vocabulary)

The nested objects inside events and transcripts use the model's own JSON vocabulary, exactly as
`Sources/ChatView/ChatModel.swift` encodes it. The rules a port must reproduce:

- Optional fields are OMITTED when nil (`explicitNulls = false`). A v1 message therefore encodes
  byte-identically whether or not the v2 fields exist.
- `ChatMessage.isStreaming` is a transient render flag and is NEVER encoded; it decodes to false.
- `ChatImage` flattens `pixelSize` to explicit `pixelWidth` / `pixelHeight` Doubles; it serializes
  by `url`, never pixel data.
- `ChatFile` decode defaults: `kind` -> `file`, `transferStatus` -> `completed`.
- `ChatTranscript`: `version` defaults to 1 when absent; `items` defaults to `[]`; `plan` defaults
  to `[]` and is encoded ONLY when non-empty; `participants` is omitted when nil. `usage` / `title`
  are omitted when nil.
- `ChatItem` uses a `type` discriminator with the exact strings: `message`, `thought`, `toolCall`,
  `image`, `system`, `error`, `memberEvent`, `callEvent`, `file`, `sessionEvent`. The payload lives
  under a key named for the case (`message`, `toolCall`, `memberEvent`, `callEvent`, `file`,
  `image`, `sessionEvent`) except `system` / `error`, which inline `id` + `text`, and `image`, which
  inlines `id` + `role` beside its `image` object.
- `transientSystem` is an EVENT ONLY. It produces the same `system` ChatItem as `system` does and
  there is no `transientSystem` item type - the difference between the two is whether the host is
  told to persist it, which is why the event tags differ and the item tags do not. Nothing decoding
  a transcript needs to know about it.
- `SessionDigest` is the one object whose ARRAYS ARE REQUIRED. `establishedFacts`, `decisions`,
  `openThreads` and `userPreferences` are non-optional in Swift, so they are written always - empty
  when empty - and demanded on decode; `summarizer`, `droppedTurns`, `verbatimTurns` and
  `unresolvedIntent` are ordinary optionals and are omitted when nil. A port that omits an empty
  array emits documents the Apple decoder rejects, and rejecting a digest rejects the item.
- Enum raw values are the wire strings: `ToolCallModel.Status.inProgress` -> `"in_progress"`,
  `PlanEntry.Status.inProgress` -> `"in_progress"`, `PermissionRequest.Option.Kind` -> the
  `allow_once` / `allow_always` / `reject_once` / `reject_always` forms. All other enums use their
  case name verbatim (`sending`, `delivered`, `read`, `failed`, `read`, `remote`, `local`, ...).

## Transcript goldens

Each is a single serialized `ChatTranscript`.

| File | Shape |
|---|---|
| `transcript-v1-minimal.json` | The pinned v1 shape (one local message). Matches `ChatTranscriptTests.testV1JSONShapeIsPinned`. |
| `transcript-v2-people.json` | A real `ChatStore` driven through the real `LocalP2PTransport` (`scenario: people`, `stepMs: 0`), then snapshotted: the seeded 1:1 conversation (timestamps, a reaction, a read/delivered ladder, an edit, a file, a voice message) plus the two-person roster. |
| `transcript-v2-group.json` | Same, `scenario: group`: adds a join member event, a missed video call, a rename member event, and the four-person roster. |
| `transcript-mixed-agentic.json` | A hand-built transcript exercising EVERY `ChatItem` case (message, thought, toolCall with `diff` + `rawInput` + `rawOutput`, image, system, error, memberEvent, callEvent, file), plus `usage`, `plan`, `title`, and `participants`. The Tier-2 pass-through gate. |
| `transcript-session-event.json` | Session markers: all three `kind`s (`started` / `resumed` / `modelChanged`), one with a full `SessionDigest`, one with a digest that is entirely empty (which pins "the four arrays are written even when empty"), and one with no digest at all. The macOS host writes these into every conversation it starts or resumes, so a reader that cannot decode one cannot open a current conversation. |

## Lossy-decode parity pair

`lossy-unreadable-items.json` is the one fixture whose INPUT is deliberately unreadable, and the one
that is hand-written rather than emitted - no encoder produces these shapes on purpose. It carries an
item with no `type` (the exact shape that cost a real user a conversation), a type from the future, a
known type over an unreadable payload, a `type` that is an object rather than a string, elements that
are not objects at all (a string, a number, a boolean, `null`, a nested array), and a real `system`
item named like a placeholder.

`lossy-unreadable-items.expected.json` is what a decoder must make of it, emitted by the Swift side:
12 items in the original order, 9 of them replaced IN PLACE by an `error` row naming what could not be
read, positional ids (`unreadable-item-<index>`, bumped to `unreadable-item-1-1` where a real item
already holds the name), and a non-persisted unreadable-item count of 9. A single unreadable entry
must cost one visible line, never the conversation.

Both are outside the `transcript-*` prefix deliberately: the goldens under that prefix must re-encode
to their own bytes, and this pair cannot - a placeholder encodes as an ordinary `error` row. That is
also the reason a host must never persist a decoded transcript back over its source.

## Routing scenarios

Each scenario is a pair:

- `scenario-NN-<name>.events.jsonl` - one JSON event envelope per line (see below), in arrival
  order. This is the input stream a transport would emit.
- `scenario-NN-<name>.expected.json` - the serialized `ChatTranscript` a `ChatStore` holds after
  routing the whole stream. This is the assertion target.

Replay contract: decode each line to an event, `route()` it through a fresh store in order, then
build a transcript from the store's final state and compare to the expected file. The transcript is
built as: `ChatTranscript(version = <the version in the expected file>, items = store.items,
usage = store.usage, plan = store.plan, title = store.title, participants = store.participants
.ifEmpty { null })`. Route the events SYNCHRONOUSLY with no clock advance: coalesced stream flushes
are applied immediately on `messageEnd`, and the debounce / expiry / throttle timers must not fire.

Transient store state that does NOT live in the transcript - `pendingPermissions`,
`typingParticipants`, `connectionState`, `configOptions`, `availableCommands`, `awaitingReply`,
`isStreaming`, `hasEarlier` - is NOT asserted by these fixtures; it is covered by the ported
`ChatStore` unit tests. Scenarios that drive such events (permission, typing, connection) bundle
them with message events so the transcript still captures a meaningful outcome and the routing
branch is exercised end to end.

| Scenario | Exercises |
|---|---|
| `scenario-01-segmented-turn` | Streamed turn, tool call interleaved; `messageEnd` stopReason nil (segment close) vs non-nil (turn end). |
| `scenario-02-implicit-open` | A bare `messageDelta` with no prior `messageStart` opens an agent message implicitly. |
| `scenario-03-thought-close` | A thought closes (and flushes) when the next item begins. |
| `scenario-04-plan-usage` | `plan` and `usage` are whole-value REPLACE (not merge); latest wins. Empty item list. |
| `scenario-05-error-path` | An `error` event appends an `error-N` item. |
| `scenario-06-permission` | A permission request routes without corrupting the transcript; the gated tool call still lands. |
| `scenario-07-received-upsert` | `messageReceived` insert, then a same-id `messageReceived` replaces in place. |
| `scenario-08-id-confirm-dedup` | `messageIDConfirmed` re-keys the optimistic item; a later confirm whose server id already exists drops the duplicate. |
| `scenario-09-status-watermark` | Direct `messageStatusChanged`; a watermark advances own messages of lower rank only, skips a `failed` one, and never regresses. |
| `scenario-10-reactions` | `reactionsChanged` fully replaces the reaction set. |
| `scenario-11-edit` | `messageEdited` sets new text + `editedAt`. |
| `scenario-12-delete` | `messageDeleted` writes a tombstone (`deleted: true`, blank text). |
| `scenario-13-member-call` | `memberEvent` and `callEvent` append. |
| `scenario-14-file-progress` | `fileAdded` then a terminal `fileProgress` (whole-Double `progress` 1.0). |
| `scenario-15-typing` | `typingChanged` on/off (transient; bundled with a received message). |
| `scenario-16-participants` | `participantsChanged` sets the roster. |
| `scenario-17-history-page` | `historyPage` prepends older items ahead of the current message. |
| `scenario-18-connection` | `connectionStateChanged` transitions (transient; bundled with a received message). |

## Event envelope schema (the contract)

Every line is a JSON object with a required `"event"` discriminator (the `ChatEvent` case name)
plus that event's fields. Fields marked optional are omitted when nil. Objects/arrays named after a
model type carry that type's model JSON (per the conventions above).

```
messageStart            { "event":"messageStart", "itemID":String, "role":String }
messageDelta            { "event":"messageDelta", "itemID":String, "text":String }
messageEnd              { "event":"messageEnd", "itemID":String, "stopReason":String? }
thoughtDelta            { "event":"thoughtDelta", "itemID":String, "text":String }
toolCall                { "event":"toolCall", "toolCall":<ToolCallModel> }
toolCallUpdate          { "event":"toolCallUpdate", "update":{ "id":String, plus any of
                          title/kind/status/contentText/diff/rawInput/rawOutput } }
permissionRequest       { "event":"permissionRequest", "request":{ "id":String, "title":String,
                          "toolCallID":String?, "options":[{ "id":String, "name":String, "kind":String }] } }
permissionResolved      { "event":"permissionResolved", "requestID":String }
resumeCheckpoint        { "event":"resumeCheckpoint", "sessionID":String, "afterSeq":Int }
plan                    { "event":"plan", "plan":[<PlanEntry>] }
usage                   { "event":"usage", "usage":<UsageInfo> }
error                   { "event":"error", "message":String, "recoverable":Bool }
system                  { "event":"system", "text":String }
transientSystem         { "event":"transientSystem", "text":String }
image                   { "event":"image", "itemID":String, "role":String, "image":<ChatImage> }
messageReceived         { "event":"messageReceived", "message":<ChatMessage> }
messageIDConfirmed      { "event":"messageIDConfirmed", "localID":String, "serverID":String }
messageStatusChanged    { "event":"messageStatusChanged", "itemID":String, "status":String }
messageStatusWatermark  { "event":"messageStatusWatermark", "status":String, "upToItemID":String }
reactionsChanged        { "event":"reactionsChanged", "itemID":String, "reactions":[<Reaction>] }
messageEdited           { "event":"messageEdited", "itemID":String, "newText":String, "editedAt":String }
messageDeleted          { "event":"messageDeleted", "itemID":String }
memberEvent             { "event":"memberEvent", "memberEvent":<MemberEvent> }
callEvent               { "event":"callEvent", "callEvent":<CallEvent> }
fileAdded               { "event":"fileAdded", "file":<ChatFile> }
fileProgress            { "event":"fileProgress", "itemID":String, "progress":Double?, "transferStatus":String }
typingChanged           { "event":"typingChanged", "isTyping":Bool, "senderID":String?, "senderName":String? }
participantsChanged     { "event":"participantsChanged", "participants":[<Participant>] }
historyPage             { "event":"historyPage", "items":[<ChatItem>], "hasMore":Bool }
connectionStateChanged  { "event":"connectionStateChanged", "state":String }
```

The `ChatEvent` cases not represented here (`sessionReady`, `currentModeChanged`,
`commandsAvailable`, `configOptionsChanged`) carry the session-option / slash-command vocabulary,
whose store effects are transient (not in the transcript) and are covered by the ported store unit
tests; they are intentionally out of the fixture schema.

## The interop gate (how a port asserts these)

Cross-language number formatting (e.g. Swift's whole Double `1` vs. Kotlin's `1.0`) means raw
string equality is NOT a safe primary check where a golden carries Double-typed model fields
(`ChatImage.pixelWidth`/`pixelHeight`, `ChatFile.progress`, `UsageInfo.costAmount`).

- Primary assertion: a numeric-normalizing parsed-tree comparison. Walk both JSON trees; when both
  sides are non-string numeric primitives, compare their numeric values; everything else (keys,
  nesting, strings, booleans, nulls, array order) compares strictly.
- Secondary assertion: Kotlin round-trip stability (decode -> encode -> decode equals the first
  decode).
- Additional (Double-free goldens only): canonical sorted-key STRING equality, to catch key-spelling
  drift early. Judge "Double-free" by the model types, not by how a number looks in the text (a
  whole Double renders as `1`).
